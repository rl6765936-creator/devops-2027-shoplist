# שיעור 5 — תשובות

## חלק א — מפת ה-cluster (האנלוגיה: מסעדה)

ה-cluster הוא מסעדה. ההנהלה (control plane) יושבת במשרד ולא מבשלת. כל node הוא מטבח, וה-pods הם המנות.

| רכיב | איפה הוא רץ | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | הדלת היחידה ל-cluster: כל בקשה (גם מ-kubectl וגם מהרכיבים עצמם) עוברת דרכו, נבדקת ונרשמת. | הדלפק בכניסה: כל הזמנה, מלקוח או מעובד, עוברת דרכו |
| etcd | הנהלה | מסד הנתונים של ה-cluster עצמו: שומר מה צריך לרוץ (הרצוי) ומה רץ בפועל. | הלוח הגדול במשרד, שעליו כתוב מה צריך להיות מוכן ובאיזה מצב כל מנה |
| scheduler | הנהלה | מחליט על איזה node ירוץ כל pod חדש, לפי המקום והמשאבים הפנויים. | מנהל המטבחים, שמחליט באיזה מטבח תוכן כל מנה חדשה לפי העומס |
| controller manager | הנהלה | לולאה שמשווה כל הזמן בין הרצוי לבפועל, ומתקנת: יוצרת או מוחקת pods. | מנהל המשמרת, שסופר כל הזמן מנות מול התוכנית ומזמין עוד אם חסר |
| kubelet | כל node | הסוכן ב-node: לוקח את ה-pods ששובצו אליו, דואג שירוצו, מרים מחדש container שקרס, ומדווח להנהלה. | ראש המטבח בכל מטבח: מקבל את רשימת המנות שלו, מוודא שהן יוצאות, ומדווח למשרד |
| container runtime | כל node | התוכנה שמריצה את ה-containers בפועל (מורידה image ומפעילה אותו). | הכיריים והתנור: מה שבאמת מבשל |
| kube-proxy | כל node | דואג שבקשה לשם של Service תגיע לאחד ה-pods שמאחוריו. | המלצר שמעביר הזמנה ל"פיצה" לאחד הטבחים שמכינים פיצה |
| coredns | כ-pods ב-namespace `kube-system`, על ה-nodes | ה-DNS של ה-cluster: מתרגם שם של Service (למשל `greeter`) לכתובת. זה אותו רעיון משיעור 4: "השם הוא הכתובת". | המרכזייה: מבקשים "המטבח החלבי" ומקבלים את השלוחה הנכונה |

## חלק ב — תרחישים

**1. scale ל-4.**
`kubectl` שולח את הבקשה ל-API server, שבודק אותה ומעדכן ב-etcd שהרצוי הוא 4. ה-controller manager (דרך ה-ReplicaSet של `web`) רואה שיש 2 מתוך 4, ויוצר 2 pods חדשים, שעדיין בלי node (`Pending`). ה-scheduler משבץ כל pod חדש ל-node. ה-kubelet ב-node שקיבל pod רואה אותו, מבקש מה-container runtime להריץ את ה-container, ומדווח ל-API server שה-pod `Running`.

**2. שלוש בלילה.**
אם ה-container של backend קרס, ה-kubelet ב-node רואה זאת ומרים אותו מחדש באותו pod (ה-`RESTARTS` עולה ב-1). אף אחד לא צריך להתעורר. אם מישהי מוחקת את ה-pod כולו, ה-kubelet כבר לא אחראי עליו. ה-controller manager רואה שיש פחות pods מהרצוי ויוצר pod חדש, וה-scheduler משבץ אותו (אולי על node אחר, ועם שם חדש).

**3. node נכבה.**
ה-kubelet של node 2 מפסיק לדווח, וההנהלה מסמנת אותו `NotReady`. אחרי זמן המתנה, ה-pods שרצו עליו נחשבים אבודים. ה-controller manager יוצר במקומם pods חדשים, וה-scheduler משבץ אותם על node 1 ו-node 3. ב-Docker Desktop יש node אחד, והוא גם ההנהלה. אם המחשב נכבה, אין לאן להעביר: כל ה-cluster נופל, וכשהמחשב עולה שוב ה-cluster עולה ומשחזר את הרצוי מ-etcd.

**4. מהכיתה לענן (EKS).**
`imagePullPolicy: Never` לא יעבוד: ה-images נבנו במחשב בכיתה ולא קיימים על ה-nodes של EKS, וה-pods ייתקעו ב-`ErrImageNeverPull`. צריך לדחוף את ה-images ל-registry (כמו ECR או Docker Hub), לשים ב-`image:` את השם המלא ב-registry, ולהוריד את `Never`. `NodePort` פותח פורט על כל node, אבל ב-EKS ה-nodes בדרך כלל ברשת פרטית ומאחורי חומות אש, ואין כתובת אחת קבועה. בענן משתמשים ב-Service מסוג `LoadBalancer` (או Ingress), שמקבל כתובת ציבורית ומחלק תעבורה בין ה-nodes.

**5. pod בודד.**
`kubectl run` יוצר pod "יתום": אין אף controller שמחזיק את המספר הרצוי שלו, ולכן כשמוחקים אותו, אף אחד לא יוצר אותו מחדש. ה-pods של `web` שייכים ל-Deployment, וה-controller רואה שחסר pod ויוצר חדש. כדי ש-stats יחזור תמיד, מריצים אותו כ-Deployment (עם `replicas`), ולא כ-pod בודד.

## בונוס — `replicas: 0`

ה-Deployment ימחק את כל ה-pods של greeter, אבל ה-Deployment עצמו ימשיך להתקיים, עם `0/0`. גם ה-Service ימשיך להתקיים, כי הוא משאב נפרד, אבל לא יהיה אף pod מאחוריו (אין endpoints). הדפדפן ב-`localhost:30090` לא יקבל תשובה: החיבור נדחה.
